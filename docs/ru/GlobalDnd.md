# Сквозной DnD: перетаскивание между разнородными штуками

Разбор задачи и предложение, а не описание готового. Ничего из этого пока не реализовано.

## Чего сейчас нет

В ките три механизма переноса «между», и все три — про однородные вещи:

| механизм | что переносит |
| --- | --- |
| `createSortableGroup` | элемент из одного списка в другой список |
| `createDumbGridGroup` | блок из одной сетки в другую сетку |
| `createDumbGridDndGroup` | то же на нативном DnD |

Каждая группа знает своих участников поимённо и умеет ровно один вид груза. Строку таблицы в блок дашборда не перетащить, узел дерева в колонку канбана — тоже. А просят обычно именно это: «перетащи товар из таблицы в заказ», «брось файл из дерева на виджет».

Свести три группы в одну общую — не выход: они отличаются не деталями, а тем, **чем ведётся жест**, и это уже разведено сознательно (см. «Две сетки: указательная и нативная» в `CLAUDE.md`).

## Что должно быть общим

Общим должен быть **контракт**, а не код. Источник объявляет, что он отдаёт; зона объявляет, что принимает; связывает их строка-тип. Тогда таблица не знает про сетку, сетка не знает про дерево, а перенос между ними работает.

```
источник: тип 'order/row',  груз { id: 'r42' }
зона:     принимает 'order/row' и 'catalog/item'
```

Ни центрального реестра, ни общего родителя, ни знания друг о друге — только совпадение строк.

## Транспорт первый: нативный DnD

Тут ничего изобретать не надо: **браузер уже и есть эта общая шина**. `dragstart` на чём угодно, `dragover` где угодно, `dataTransfer` несёт груз. Работает между компонентами, между фреймами, между окнами и даже между приложениями.

```ts
// источник
ev.dataTransfer.setData('application/x-dumb-kit+order/row', JSON.stringify({ id }))
ev.dataTransfer.setData('text/plain', 'Заказ №42')   // чтобы бросить в чужое поле

// зона
const accepted = [...ev.dataTransfer.types].some((t) => zone.accepts(t))
```

**Грабля, которая определяет весь API.** Во время `dragover` груз прочитать НЕЛЬЗЯ — `getData()` там возвращает пустую строку, это защита от подглядывания. Доступен только список **типов** (`dataTransfer.types`). Значит решение «принимаем или нет» обязано приниматься по типу, и тип — это и есть контракт. Груз читается только в `drop`.

Отсюда следствия:

- тип должен нести достаточно, чтобы решить, не читая груза (`order/row`, а не `row`);
- типы регистрозависимы не везде: Chrome приводит их к нижнему регистру, так что писать только строчными;
- `text/plain` стоит класть всегда — иначе жест не начнётся в Firefox, и груз нельзя будет бросить в обычное текстовое поле.

## Транспорт второй: указательные события

Тач нативного DnD не знает, поэтому для пальца нужен свой транспорт. Здесь общей шины нет — её приходится держать самим: модульный реестр зон с их прямоугольниками, снятыми через `IntersectionObserver`, и хиттест арифметикой в кадре. Ровно это уже делают `sortableGroup` и `gridGroup`.

Разница с нативным транспортом только в том, кто отвечает на вопрос «над чем курсор». Контракт — тот же.

| | нативный | указательный |
| --- | --- | --- |
| хиттест | браузер | наш реестр зон |
| тач | нет | да |
| между окнами | да | нет |
| груз во время движения | только тип | весь |
| цена | 0 | снимок зон на старте жеста |

## Как это выглядит без Solid

Ядро — две функции, ни одного импорта фреймворка. Так же, как устроены `sortableCore` и `gridCore`.

```ts
import { createDragSource, createDropZone } from '@solid-dumb-kit/dnd-core'

const stopSource = createDragSource(rowEl, {
  type: () => 'order/row',
  data: () => ({ id: row.id }),
  text: () => row.title,          // для чужих полей и Firefox
})

const stopZone = createDropZone(basketEl, {
  accepts: (type) => type === 'order/row',
  onOver: (pos) => highlight(pos),
  onDrop: (payload, pos) => addToBasket(payload.data, pos),
})
```

Обе возвращают функцию отписки — единственное, что потом нужно фреймворку.

Транспорт выбирается пропом, а не отдельным пакетом:

```ts
createDropZone(el, { transport: 'pointer', ... })   // по умолчанию 'native'
```

## Как это выглядит с Solid

Solid даёт `use:`-директивы — под такой контракт они ложатся точно, потому что директива это и есть «повесить что-то на элемент и снять при размонтировании».

```tsx
import { dragSource, dropZone } from '@solid-dumb-kit/dnd'

<tr use:dragSource={{ type: 'order/row', data: () => row }} />

<div use:dropZone={{
  accepts: (t) => t === 'order/row',
  onDrop: (p) => setBasket((b) => [...b, p.data]),
}} />
```

Внутри — те же `createDragSource`/`createDropZone`, обёрнутые в `onCleanup`. Слой ровно в три строки, как `solid.ts` у остальных пакетов: под Solid 2 или другой фреймворк переписывается только он.

Реактивность заходит естественно: `accepts` и `data` — функции, значит читаются в момент вызова и видят свежие сигналы без подписок.

## Что придётся решить

**Подсветка зоны.** Нативный `dragenter`/`dragleave` считать вложенность не умеет: вход в дочерний элемент выглядит как выход из родителя, и подсветка мигает. Лечится счётчиком входов — это ровно та часть, которую делала за нас библиотека Atlassian и которую придётся написать самим (десяток строк).

**Позиция внутри зоны.** Список хочет знать «между какими», сетка — «в какую ячейку». Это не дело общего слоя: зона получает координаты и решает сама. Иначе общий слой начнёт знать про списки и сетки, и мы вернёмся к тому, от чего уходили.

**Отмена.** Escape и бросок мимо зоны обязаны возвращать всё на место. У нативного транспорта это `dragend` без предшествующего `drop`, у указательного — своя проверка.

**Движение.** FLIP уже общий (`@solid-dumb-kit/shared`), и обоим транспортам подходит без изменений.

## Что это даёт киту

Три нынешних группы становятся частными случаями одного контракта: список принимает `list/item`, сетка — `grid/block`. Существующие API можно оставить как есть, а общий слой добавить рядом — они не конфликтуют.

И появляется то, чего сейчас нет вовсе: перенос между **разными** видами виджетов, без единой строчки, знающей про оба.

## Чего делать не стоит

- **Единого «менеджера DnD» на приложение.** Он превращается в глобальное состояние, которое надо сбрасывать, и ломается на двух независимых жестах.
- **Груза в типе.** Соблазн закодировать данные прямо в строку типа (`order/row?id=42`) — читается в `dragover`, да. Но типы уходят в системный буфер обмена и видны другим приложениям.
- **Общей позиции в контракте.** «Куда именно» знает только зона; общий слой должен передавать координаты и не более.

## Порядок работ, если делать

1. `dnd-core` — контракт и нативный транспорт, без фреймворка;
2. проба в `examples/lab/` — таблица и сетка, перенос строки в блок;
3. указательный транспорт тем же контрактом;
4. `use:`-директивы для Solid;
5. и только потом — переводить ли существующие группы на общий слой.
