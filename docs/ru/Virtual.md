# Длинные списки

Два примитива из `@solid-dumb-kit/shared`: `createVirtualizer` решает, **какие**
элементы рисовать, `createRowIndex` — **что** лежит под номером элемента, когда
строк миллион и их надо отсортировать или отфильтровать.

```tsx
import { createVirtualizer, createRowIndex } from '@solid-dumb-kit/shared'
```

Живьём — вкладка [`#virtual`](https://russelgal.github.io/solid-dumb-kit/#virtual),
исходник в [`examples/data/virtual.example.tsx`](../../examples/data/virtual.example.tsx).

## `createVirtualizer` — окно без единого замера

Ходовые виртуализаторы измеряют элементы: `getBoundingClientRect` по строке,
чтобы узнать её высоту. На тысяче строк это тысяча forced layout — ровно то,
что киту [запрещено](../../CLAUDE.md). Здесь размер строки **заявлен**, и окно
считается арифметикой.

Из DOM берётся только `scrollTop` (это не forced layout — браузер отдаёт его из
уже посчитанной раскладки) и размер видимой части через `ResizeObserver`.
Элементы не измеряются никогда.

```tsx
const [range, setRange] = createSignal<VirtualRange>({ start: 0, end: 0, offset: 0, total: 0 })

const v = createVirtualizer({
  count: () => rows().length,
  itemSize: () => 28,          // высота строки вместе с зазором
  scroller: () => scrollerEl,
  onChange: setRange,
})
onCleanup(() => v.destroy())
```

`VirtualRange` — четыре числа: `start`/`end` (какие индексы рисовать), `offset`
(насколько сдвинуть нарисованное вдоль оси) и `total` (размер распорки, которая
держит полосу прокрутки).

| Опция | Зачем |
| --- | --- |
| `count` / `itemSize` | сколько элементов и какой каждый — основа арифметики |
| `itemSizes` | размеры **поштучно**, когда ряды разной высоты, но она известна заранее (например, «строка × число этажей»): накопленные суммы и бинарный поиск вместо деления |
| `columns` | сколько элементов в ряду — для сеток плиток |
| `axis` | `'x'` — окно считается по `scrollLeft` и ширине; для шкал времени и всего, что едет вбок |
| `lead` | сколько пикселей стоит **перед** первым рядом в том же скроллере: липкая колонка, шапка. Без поправки окно уезжает ровно на её размер |
| `overscan` | сколько рядов рисовать про запас (по умолчанию 3); меньше двух брать не стоит — при быстрой прокрутке появляется белая полоса |
| `maxHeight` | потолок распорки, см. ниже |

`refresh()` пересчитывает окно принудительно — зови его, когда сменилось число
элементов или размер строки; движок сам узнаёт только про прокрутку и размер
вьюпорта.

### Потолок высоты

Высота элемента не бесконечна: Chrome обрезает примерно на 33.5 млн пикселей,
Firefox — около 17.8 млн. При строке в 28px это всего ~600 тысяч строк, дальше
распорка молча перестаёт расти, а полоса прокрутки — соответствовать
содержимому.

Поэтому распорка зажимается `MAX_SCROLL_HEIGHT` (15 млн, с запасом под самый
строгий браузер), а прокрутка перестаёт быть один к одному: `scrollTop`
растягивается до виртуальной высоты списка. Расплата — строки внутри одного
пикселя полосы перескакивают через несколько позиций; на таких объёмах это ровно
то же, что делает нативная полоса прокрутки, только честнее.

`scrollOffsetFor` умеет обратный пересчёт — передай ему `count`, иначе прокрутка
к строке промахнётся тем сильнее, чем длиннее список.

### Пул узлов

Виртуализация сама по себе снимает только количество узлов. Если рисовать окно
обычным `<For>` по индексам, то при прокрутке старые строки удаляются, а новые
создаются — и счётчик созданных узлов растёт всю дорогу.

Пул создаёт узлов ровно столько, сколько влезает в окно, и дальше меняет в них
текст и `transform`: слот держит ту позицию окна, у которой остаток от деления
на размер пула равен его номеру, поэтому при сдвиге окна на строку меняется один
слот, а не всё окно. Замер на одинаковой прокрутке (20 шагов по 40 строк):

| Как рисуем | Узлов в разметке | Создано узлов за прокрутку |
| --- | --- | --- |
| `<For>` по окну | 27 | 594 |
| пул слотов | 29 | **29** |

Реализация — в примере, а не в ките: раскладка строки у каждого своя, а сам
приём — двадцать строк кода.

## `createRowIndex` — сортировка и фильтр вне главного потока

На тысяче строк вопрос не стоит: сортируй массив как угодно. На миллионе
`array.sort` занимает главный поток на секунды, и всё это время страница не
отвечает — не прокручивается, не перерисовывается, не реагирует на клики.

```tsx
const index = createRowIndex({
  onResult: (r) => { setOrder(r.order); setShown(r.matched) },
  onProgress: (p) => setProgress(p.done),
})

index.setData({
  count: values.length,
  columns: { value: { kind: 'number', values } },   // Float64Array или string[]
})

index.query({
  filter: { column: 'value', contains: '137' },     // либо min/max
  sort: { column: 'value', dir: 'desc' },
})
```

Результат — `Uint32Array` **номеров строк**, а не переставленные данные: 4 байта
на строку против копирования объектов. Сами данные никто не двигает.

Работа идёт в воркере, который собирается из строки прямо в пакете (отдельный
файл пришлось бы отдавать потребителю рядом с бандлом и объяснять каждому
сборщику, как его найти). Не завёлся воркер — считаем на главном потоке теми же
порциями; `threaded` скажет, что вышло на самом деле.

### Почему сортировка своя

Встроенный `sort` остановить нельзя, а пока он идёт, воркер не читает входящие
сообщения и не может отменить устаревший запрос. Набор в поле фильтра шлёт запрос
на каждую букву — без отмены к последней букве в очереди стоит десяток мёртвых
сортировок.

Поэтому слияние снизу вверх с сохранением состояния между порциями: работу можно
бросить на полуслове. Между порциями воркер уступает очереди сообщений, и отмена
успевает сработать.

### Общая память

Когда страница изолирована (`crossOriginIsolated`), колонки и массив порядка
живут в `SharedArrayBuffer`: данные не копируются в воркер вовсе, а строки,
прошедшие фильтр, видно **пока фильтр ещё идёт** — такой ответ приходит с
`partial: true`. Без изоляции всё то же работает на копиях, результат едет обратно
`transfer`ом. Проверить, что вышло, — поле `shared`.

Изоляция включается заголовками `COOP`/`COEP` на каждом ответе сервера. Статике
вроде GitHub Pages их взять неоткуда, поэтому витрина ставит их сама, через
service worker ([`playground/public/coi-sw.js`](../../playground/public/coi-sw.js)) —
приём известный, им живут сборки на WASM. `COEP` там `credentialless`, а не
`require-corp`: под `require-corp` любая картинка со стороннего домена без
заголовка `CORP` просто не загрузится.

### Замеры

Миллион строк, значение — число, фильтр по подстроке его записи:

| Что | Воркер | Главный поток |
| --- | --- | --- |
| сортировка по убыванию | 106–114 мс | 122 мс |
| фильтр (1003 совпадения из 1 000 000) | 17 мс | — |

Разница не в самих числах — работа одна и та же. Разница в том, что в первом
случае эти сто миллисекунд не отнимаются у прокрутки.

## Что осталось за бортом

- **Разновысокие списки без заявленных размеров.** Если высоту строки можно
  узнать только измерив её, это другой примитив с другой ценой, и его здесь нет
  намеренно. `itemSizes` берёт размеры от потребителя, а не из DOM.
- **Текстовые колонки в общей памяти.** Строки в `SharedArrayBuffer` не положить,
  они уезжают копией; числовые колонки — нет.
- **Сортировка текста** идёт по кодовым точкам (`<`, `>`), а не через
  `localeCompare`: последний на миллионе строк стоит дороже всей остальной
  работы вместе взятой.
